# API와 Mock 어댑터

기획서에 실제 계약 원본, endpoint, 요청·응답·오류, 인증·권한, API 환경과 갱신 시점을 연결한다. 프론트 DTO를 추측해서 실제 계약처럼 굳히지 않는다. 타입 생성 도구가 있으면 기존 생성 경로를 사용하고 생성 파일을 손으로 고치지 않는다.

MSW, Playwright routing, 기존 fixture 등 현재 도구를 재사용한다. fixture에는 API 계약의 필수·nullable 필드와 페이지 구조를 반영하고 상태를 구분할 수 있는 데이터 이름을 쓴다.

재현할 실패는 기능 위험에 맞춰 고른다. 예: 검색 응답 역전, 상세 404, 로그인 401, 권한 403, 중복 처리 409, 제한 429, 서버 500, timeout, 오프라인. 모든 기능에 모든 코드를 억지로 적용하지 않는다.

실제 API QA에서는 CORS·쿠키 SameSite·인증·갱신·권한·응답 형식·실서버 오류를 확인한다. 읽기 검증과 쓰기 검증의 테스트 계정을 분리하고 실제 데이터 오염을 피한다. 요청 collection이 필요하면 QA에서 사용한 요청을 재사용하되 비밀값은 제외한다.

자동 검증은 응답의 출처 표식과 하네스의 fixture 사용 기록을 대조한다. 함께 관측되면 `mixed`, 근거가 부족하면 `unknown`, API 호출이 없는 시나리오는 `none`으로 남긴다. `requireLiveApi`를 켜면 입증된 `live`만 ready를 통과한다. 규칙과 기대값은 [브라우저 자동화](browser-automation.md)에 따라 설정한다.
